# Workshop publishing from the CLI

What is proven on this machine (Arma Reforger 1.8.0.13, Workbench from "Arma Reforger Tools").

## Updating an existing item is fully headless

`tools/publish-addon.ps1 -Auto` runs Workbench with:

```
-wbModule=ResourceManager -addonsDir <game addons>,<deps> -gproj <project>
-publishAddon -publishAddonDir <bundle> -publishAddonVersion <ver>
-publishAddonChangeNote <note> -wbSilent -noThrow
```

The backend accepts it and the revision appears on the Workshop changelog. The one
catch found the hard way: **the public pages are CDN-cached**. Fetching
`/workshop/<id>` and `/workshop/<id>/changelog` without a cache-busting query
returns a stale version and a stale changelog, which looks exactly like "the upload
did not happen". Always verify with something like `?cb=<random>`:

```
https://reforger.armaplatform.com/workshop/A1D0D0D0C0FFEE01?cb=778812
```

## CLI switches that exist (strings of the Workbench exe)

```
-publishAddon  -publishAddonDir  -publishAddonVersion  -publishAddonChangeNote
-publishAddonChangeNoteFile  -publishAddonPreviewImage  -publishAddonScreenshots
-publishAddonCacheDir  -publishCert
```

There is no switch for title/summary/description/license.

## Creating a NEW item needs `summary`, which the CLI cannot supply

`WorkshopApi/CreateAssetUpload` returns

```
400 ValidationError: data.asset should have required property 'summary'
```

The bundle manifest is generated by Workbench from the project (`ID`, `GUID`,
`TITLE` from `addon.gproj`) plus, for an existing asset, the metadata it fetches
from the backend. Injecting `asset.summary` into `manifest.json` before publishing
is pointless: Workbench re-bundles and drops it.

`GameProject` has no summary/description keys either (the schema strings in the exe
list only ID, GUID, TITLE, Dependencies, Configurations, EngineUserSettingsPath...).

So: create the item once in the Publish dialog; every later version can be pushed
headless. This is a backend requirement, not a missing flag.

### Headless alternative: reuse an existing item

Because the only blocked operation is *creating* the asset, publishing a new mod
headlessly means pointing the project's `GUID` at an item that already exists.
Claimed versions cannot be reused:

```
400 apiCode="workshopApi.assetVersionAlreadyExists"
Version 1.0.0 of asset <GUID> already exists
```

so bump above the item's highest version. The item keeps its old title/summary until
someone edits them in the dialog, and existing subscribers get the new content.

## A fabricated workshop-state file makes a local mod "corrupted"

The game treats an addon as Workshop-managed when
`profile\.save\app<APPID>_user<STEAMID>\workshop\I<GUID>.json` exists. Writing that
file for a mod that is not on the Workshop (to force it "enabled") makes the game try
to verify/download it and report the addon as corrupted. Local test addons need just
the folder with `addon.gproj` + `data.pak` + `resourceDatabase.rdb` and the GUID in
`-addons`.

## Workbench leaves no token on disk

Searched both profiles (`Documents\My Games\ArmaReforger*`) and `AppData\Local` for
JWT/cookie material: nothing. Session lives in memory, keyed by the Steam identity.

## Workshop API surface (from the exe / generated bindings)

Client-side endpoints:

```
v4/asset/upload/config | create | commit | getDetails
v4/asset/getDetails | list | getListRemainder
v4/asset/revision/getDetails | getListRemainder
v4/asset/download/listFull | listPartial | resolveVersionList
v4/asset/addRating | removeRating | addSubscriptions | removeSubscriptions
v4/asset/addBlocks | removeBlocks | report | stats/countDownloads
v4/comment/list | create | delete | addReaction | removeReaction
```

**There is no asset delete endpoint in either the game or Workbench client.** Deleting
a published item is a website/account action, so it cannot be scripted through
Workbench at all - it needs an authenticated browser session (Steam OpenID), after
which the site's own request can be replayed from that tab.

## Editor placement: two hooks, not one

Game Master places single entities through the content browser, which resolves the
prefab via `SCR_PlacingEditorComponentClass`:

```
override ResourceName GetPrefab(int index)         // index -> prefab, used when spawning
override int GetPrefabID(ResourceName prefab)      // prefab -> index, used when selecting
```

Hooking only `GetPrefab` makes the browser hand the substituted prefab back, the
registry lookup fails and placement dies silently with

```
Cannot initiate placing of prefab @"{...}...", it's not registered in placeable entities!
```

Substituting the browser list (`GetPrefabs`) instead hides the units entirely, because
the replacement prefabs carry their own faction and fall outside the faction filter.

## Same-path prefab overrides DO bind when GUIDs match

"Modern Russians" ships 55 vanilla `Character_USSR_*.et` at the vanilla paths with
**no `.meta` files**, and its `resourceDatabase.rdb` stamps the same GUIDs as the base
game (`Character_USSR_AAT.et` = `631158F6898738A4` in both). That is why the override
wins. A mod that ships a same-path prefab with a *different* GUID silently loses.
